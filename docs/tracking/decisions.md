| D59 | EP2 marketing pages use verbatim prototype CSS via per-page CSS Modules, not Tailwind utilities — exception to `frontend.md §7.2`. Shared shell styles (Navbar, Footer, WhatsApp float, sticky bar) go in `globals.css`; per-page styles are co-located as `page.module.css` beside each `page.tsx` with class names 1:1 matching the prototype HTML | Prototype reuses identical generic class names (`.hero`, `.grid`, `.cta`) with page-specific overrides; consolidating into one stylesheet causes selector collisions that break pixel fidelity. CSS Modules scope each page independently, preserving an exact visual match without Tailwind translation risk | 2026-06-06 |
| D60 | Commit messages for this project drop the `[Phase 1]` / `[Phase N]` prefix — plain Conventional Commits `type(scope): description` only. Overrides `RULES.md §6.2`. Branch naming `phase-1/…` is unchanged | Prefix was redundant with branch name and conflicted with standard Conventional Commits tooling; removing it keeps messages clean and machine-parseable | 2026-06-06 |
| D61 | Phase 1 contact form uses **Resend via a Next.js Route Handler** (`client/src/app/api/contact/route.ts`), not a separate Express server and not EmailJS. The handler runs server-side as a Vercel serverless function deployed with the frontend. `RESEND_API_KEY` is server-only (never `NEXT_PUBLIC_`). Email body uses **React Email** components. Admin-only notification to `bhoure05@gmail.com`; no user auto-reply; no DB persistence. **Rate limiting IS in Phase 1** — in-memory sliding window, 3 req / 60 min / IP (`client/src/lib/rate-limit.ts`), keyed on `x-forwarded-for`; best-effort on serverless (per-instance, resets on cold start), swap-ready for Upstash Redis for hard distributed enforcement. Aligns with the locked Resend provider (`integration SKILL`); the only deviation is endpoint location (Next Route Handler instead of Express `/api/v1/contact`) — the Express endpoint is introduced when the full server stack lands in Phase 2. **Supersedes the earlier EmailJS form of this decision.** | A Next.js Route Handler needs no separate backend deployment — it ships with the Vercel frontend at zero extra hosting cost — while keeping the Resend API key off the client, matching the locked architecture, and avoiding a rewrite before Phase 2. EmailJS exposed its key in the browser bundle and was a throwaway workaround. | 2026-06-07 |
| D62 | Global toast library for Phase 1 is **react-hot-toast** (not sonner). Mounted via `<Toaster>` in root `layout.tsx`. | Simpler API than sonner, zero configuration for the Phase 1 use case (form error/success toasts only). | 2026-06-07 |
| D63 | Both `client/` and `server/` are deployed on **Hostinger Business plan** as separate Node.js applications — `gstnoticesupport.in` (frontend) and `api.gstnoticesupport.in` (backend). Replaces the original Vercel + Railway plan. Vercel and Railway are no longer used. Cloudflare remains in front of both domains for CDN, WAF, and DDoS protection. Process lifecycle is managed by Hostinger hPanel Node.js manager (no PM2). Deployments are manual: SSH → `git pull` → build → hPanel restart. **Partially supersedes D61**: the contact form Route Handler now runs as part of a persistent Next.js server process on Hostinger, not a Vercel serverless function; in-memory rate limiting remains valid since the process is persistent (no cold-start resets). | Low initial traffic makes Hostinger Business plan sufficient. Consolidating both apps on one hosting account reduces cost and operational complexity. Cloudflare free tier covers CDN and WAF regardless of origin host. | 2026-06-09 |
| D64 | `GET /user/payment-history` uses **offset-based pagination** (default limit 20, max 100). Invoice display links to the **Razorpay-generated receipt URL** — no in-house PDF invoice generation. Data source: `payment_records` joined with `bookings`. Resolves LLD §9 Q10 and Q11. | Offset pagination is sufficient for this platform's expected payment history volume (users rarely exceed 5–10 records). Razorpay already generates receipts; duplicating invoice generation adds infra complexity for no user benefit. | 2026-06-16 |
| D65 | Login security-alert email includes **IP address** (`req.ip`) and **sanitized User-Agent string** (truncated to 200 chars) only. No geolocation API lookup, no PII beyond what is already in the session. Email body: "A login was detected from IP `x.x.x.x` using `Chrome on Windows`" + "This wasn't me" invalidation link. Resolves LLD §9 Q4. | Geolocation APIs introduce a third-party dependency, latency, and potential PII leakage. IP + User-Agent satisfies the security-signal intent without violating the "no PII in logs" rule. Device fingerprinting deferred to Future Work (LLD §10). | 2026-06-16 |
| D66 | `payment_records` table gains two fields: `source` (enum: `webhook \| verify \| admin_override`, not null, default `webhook`) and `performed_by_admin_id` (nullable FK → `users.id`). When admin calls `mark-paid`, a new `payment_records` row is inserted with `source = admin_override` and `performed_by_admin_id = req.user.id`. Razorpay Fetch Payment API must confirm `captured` status before the row is written — no blind override. Resolves LLD §9 Q5. **Amends LLD §4 `payment_records` schema.** | Storing audit info in `payment_records` keeps all payment history in one table. The `source` field lets ops distinguish webhook-driven vs user-verify vs admin-override captures without a separate audit log table. | 2026-06-16 |
| D67 | `POST /auth/complete-profile` (one-time step after OTP verification) collects **`name` and `phone`** only. All other per-case fields (GSTN, org name, filing-for) are captured per-booking, not on the profile. `PATCH /user/profile` (Phase 2/EP15) allows updating name and phone later. Resolves LLD §9 Q8 and Q13. | Minimising the one-time completion step reduces drop-off immediately after signup. Booking-specific data belongs on the booking, not the user profile, to support repeat bookings with different GSTNs. | 2026-06-16 |
| D68 | **Phase 2 auth resolutions.** (a) **Response envelope aligned to `api_contract.md`**: `ApiError` carries a named `code`; errors serialise as `{ success:false, error:{ code, message, details? } }` and success as `{ success:true, message?, data }`. Supersedes the flat `{ success, data, error, statusCode }` shape in `backend.md §3.3`/§7 and the Phase 0 changelog. (b) **No refresh-token rotation** — `POST /auth/refresh` mints only a new access token; the 7-day refresh token/cookie is unchanged (`api_contract.md §1.6`), overriding the `backend_plan.md`/TASKS "rotation on every refresh" wording. (c) **`User.phone` column added** (nullable, migration `add_phone_to_users`) — required by complete-profile (D67) and already referenced by `userRepository.updateProfile`; deviates from the roadmap's "Phase 2 has no DB changes". (d) **Soft-delete guard reimplemented as a Prisma client extension (`$extends`)** — Prisma 6 removed `$use` middleware. | (a) The frontend switches on `error.code`; a named-code nested object is the contract the client consumes. (b) Matches the declared source of truth and avoids invalidating valid sessions on every silent refresh. (c) The field is structurally required for the locked profile flow. (d) `$use` no longer exists in the pinned Prisma 6.19.3 client. | 2026-06-16 |
| D69 | **404 for foreign-booking lookups in user-facing endpoints.** `GET /bookings/:id` and `POST /bookings/:id/cancel` use an ownership-baked repository query (`findByIdAndUserId`) that returns `null` for both non-existent and other-user bookings. Both cases return `404 NOT_FOUND`. The `api_contract.md §3.3` lists `403 FORBIDDEN` for other-user access — this collapses it to 404 to avoid existence leaks. If strict 403/404 distinction is required in future, add a separate `findById` (no userId filter) and compare. | No existence leak — a malicious user cannot determine whether a booking ID exists by observing 403 vs 404 responses. The booking test runner documents this. | 2026-06-17 |
| D70 | **Booking state machine introduced as a pure, reusable module** at `server/src/services/booking-state-machine.ts`. `ALLOWED_TRANSITIONS`, `canTransition`, `assertTransition`, and `assertUserCancellable` live here and are imported by the booking service. Phase 5 (payment→filing) and Phase 6 (admin transitions) must import from this module rather than re-deriving the transition map. | A single source of truth for legal transitions prevents drift across phases. Pure module (no Prisma, no req/res) is unit-testable in isolation. | 2026-06-17 |
| D71 | **GSTN validation uses format-only regex** `^[0-9]{2}[A-Z]{5}[0-9]{4}[A-Z][1-9A-Z]Z[0-9A-Z]$` at the Zod schema layer. No external GSTN verification API is called. The regex enforces structural format (state code, PAN structure, entity code, Z checksum placeholder, checksum digit) but does not verify against the GST portal. | LLD specifies format-only validation; no external dependency is introduced for a non-blocking intake step. Portal verification can be added in a future phase. | 2026-06-17 |
| D72 | **Phase 4 document-handling resolutions.** (a) **Pre-signed URLs disable SDK request checksums** — `S3Client` is created with `requestChecksumCalculation: 'WHEN_REQUIRED'` / `responseChecksumValidation: 'WHEN_REQUIRED'`. (b) **Encryption is applied by bucket-default SSE-S3, not a per-request `ServerSideEncryption` header** — the PUT command no longer signs an SSE header. (c) **No `nanoid`/`date-fns` dependency** — the 4-char key suffix uses `crypto.randomBytes` and the `yyyyMMdd` stamp uses native `Date`, since `nanoid` v5 is ESM-only and the server is CommonJS. (d) **`upload-url` rate limit is 7/hr** per `api_contract.md §4`, superseding the `15/hr` note in TASKS/backend_plan. (e) **IAM is object-scoped only** (`PutObject`/`GetObject`/`DeleteObject` on `bucket/*`, no `ListBucket`). (f) **`confirm-upload` rejects an `s3Key` not prefixed `{userId}/{bookingId}/`** so a confirm cannot reference an arbitrary object. | (a)+(b) Recent `@aws-sdk/client-s3` bakes a CRC32 checksum into the signed URL that breaks a browser PUT streaming the real body; S3 also applies SSE-S3 to every object by default, so signing an SSE header only adds a CORS/header burden on the client. (c) Avoids an ESM/CJS interop break and two dependencies for trivial helpers. (d) The contract is the authoritative source. (e) Least privilege — the app never lists the bucket. (f) Defence-in-depth against confirming a forged key. | 2026-06-23 |
